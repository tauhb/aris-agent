# What the DeepSeek Harness (dsh 0.2.1-rc.2) already gives a "persistent bot thread", and what is missing

Scope: read-only study of the `@deepseek-ai/dsh-*` packages under `/home/user/aris-agent/node_modules/.pnpm/@deepseek-ai+dsh-<pkg>@0.2.1-rc.2_*/node_modules/@deepseek-ai/dsh-<pkg>/` (README.md, `lib/types/*.d.ts`, a little compiled JS). Nothing was run or modified. Statements are from the READMEs/d.ts unless tagged **[inference]**. Short package names below omit the `@deepseek-ai/` scope.

Goal under evaluation: each aris bot = one persistent teammate with ONE continuous conversation; user messages steer a running turn; human waits (approval, question, takeover) release compute and resume exactly; long history is compacted; background and scheduled work posts into the same thread.

## 0. Verdict in six lines

1. A dsh **Session is already an immortal, append-only, crash-safe event log** (`dsh-session` + `dsh-session-persistence-jsonl` + `dsh-session-checkpoint-policy`). There is no size cap or rotation; compaction is the designed answer to length. One session per bot is natively supported. What dsh does not provide is the "one session per bot" policy; that is an aris mapping (aris already does it per channel thread in `packages/aris-channels/src/hub.ts`, `sessionFor(bot, key, ...)`).
2. **Steering is native**: `Agent.steer()` (joins the running turn at the next step boundary), `Agent.followup()` (queued as its own later turn), `Agent.inject()` (context, no wake), `Agent.cancel(cause, {keepInbox})`. The inbox is durable (`agent/inbox/spliced` events). Concurrent prompts never run in parallel; they queue.
3. **Human waits are NOT release-and-resume for approvals.** `ApprovalService.request()` awaits an in-process promise inside an open turn. A daemon restart turns the pending tool call into `TOOL_OUTCOME_UNKNOWN` and the turn is closed as interrupted. Only `ask_user_question` in `mode: timed` (`UserQuestionService.askTimed()`) has a true "release the model, answer later, reply steers back in" path, and it is the template for what aris should build for approvals.
4. **Background work**: `dsh-schedule` is durable and restores a cold session to deliver (best fit for "scheduled work posts into the same thread"). `dsh-jobs-local` jobs are process-local and die on restart, but their completion notice wakes the owner (`dsh-tool-jobs`). Subagents deliver a completion notice to the parent; the parent must be live. Agent teams are experimental and single-process.
5. **Compaction exists and is cache-aware**: `dsh-compaction-basic` triggers at `floor(min(W*0.8, W-O-65536))` tokens, keeps the newest 16% of `W-O` verbatim, replaces the older span with one summary, and replays the parent prefix byte-for-byte so the summarizer call hits DeepSeek's cache. A checkpoint itself invalidates the cache from the first shadowed token (inherent). With a 1M-token window it fires rarely.
6. **Missing as a ready-made unit**: durable out-of-turn approval; a release-compute wait (turn state parked, agent disposed, resumed later); per-thread idle eviction policy; durable parent mailbox for subagent/job results; cross-process leases; an owner-per-bot or multi-principal policy for a bot's thread. All can be built as aris plugins on `ctx.agents`, `ctx.sessionController`, `ctx.userQuestions`, `ctx.schedule`-style services, the `agent/*` event waterfalls, and `ctx.remoteAccess.registerPolicy`.

## 1. Session model

### 1.1 What a session is
- `dsh-session` (README, `lib/types/types.d.ts`): a `Session` is an **append-only, typed `SessionEvent` log**. Model history is *derived* (`session.deriveMessages()`) from "surface" events (`system/message`, `developer/message`, `user/message`, `assistant/message`, `tool/result`). Everything else (turn/step boundaries, `request/header`, `request/context`, `approval/asked|decided|policy`, `agent/inbox/spliced`, `compaction/*`, `image/offload`, `job/*`, plugin records `plugin:<owner>/<record>`) is log-only.
- Creation/lookup: `ctx.sessions.create(id, {meta})`, `get`, `list`, `fork(source, boundary?, childId?)`, `flush(session)`. `session.append(type, data, {surfaceOp})` is the only writer; payloads must be lossless JSON.
- Replacement: `surfaceOp: {op:'replace', startSeq, endSeq}` shadows older surface nodes without deleting log rows. This is how compaction works.
- Fork: `buildForkSeed` (`dsh-session/fork`) copies an exact event prefix, adds synthetic error tool results for the open step and a `forked` turn end. Exposed as `ctx.sessionController.fork({sessionId, atSeq?})`.
- Plugin state in a session: `appendPluginRecord` is restricted to packages under `packages/experimental/` in dsh's own repo ("Plugins outside this repository must not call it either"). So an aris plugin cannot legitimately write custom records into the dsh log; use `dsh-session-projection` units (read side) and aris' own store (write side), or `user/message` with a `MessageSource` for model-visible facts.

### 1.2 Can a session live forever?
- **Size/rotation**: none found. `dsh-session-persistence-jsonl` keeps one `.jsonl.zstd` file per session under `<root>/--<normalized-cwd>--/<encoded-id>/` (current format version generation file + `session.lock`). Its limitations list says "Nothing deletes session files". No max-bytes/rotation option exists in its config (`root`, `compression`, `listConcurrency`).
- **Practical limits** (the real "forever" constraints):
  - Cold resume replays the whole log: "Exact reads replay whole logs" (`dsh-session-query` limitations); `ctx.agents.resume()` reads the stored log through its write handle. Cost grows with total events, not with the compacted surface **[inference: resume of a multi-year thread is O(log)]**. Compaction does not shrink the file.
  - `session-projection-cache` (`dsh-session-projection-cache`) can seed the fold from persisted rows to speed cold reads of projections.
  - Format migration is handled by `dsh-session-format-*` chain and applied on write-open.
- **Recommendation [inference]**: for a bot that lives for months, plan a *rollover by fork*: `sessionController.fork({sessionId, atSeq})` at a quiet point, or start a new session seeded by a summary, and keep aris' bot-to-session pointer outside dsh. Compaction alone keeps model context bounded but not the log file or replay time.

### 1.3 Compaction
Packages: `dsh-compaction` (service contract, checkpoint marker), `dsh-compaction-basic` (the backend), `dsh-compaction-tool-result-pruner`, `dsh-compaction-image-offload`, `dsh-command-compact` (`/compact`).
- **When**: with `auto: true` (default) a serial `agent/pre-step` listener prices the latest routed request through `ctx.tokenMeter` (`dsh-token-meter`) *before request derivation*. Trigger = `floor(min(W * thresholdRatio(0.8), W - O - headroomTokens(65536)))` where W is the route's context window, O the effective output cap. A second trigger: `agent/request-error` with provider-confirmed `CONTEXT_WINDOW_EXCEEDED` -> one maximal head reduction and a retry (`maxOverflowRetries: 1`). Manual: `/compact` (only when idle; "unavailable" mid-turn) or `compactRegion` (needs an open turn).
- **What it keeps**: the system prompt (surface node 0 is never shadowed), the newest `retainRatio` (0.16) of `W - O` verbatim at a balanced unit boundary (tool call/result pairs are indivisible). Everything older is replaced by one `user/message` summary wrapped in `<compacted-summary>` with a fixed checkpoint preamble. Summary format is a fixed Markdown structure (Primary Request and Intent, Key Technical Concepts, Files and Code, Errors and Fixes, Pending Jobs, Current Work, Next Step, Critical Context). Summarizer provider/model are configurable (`summarizationProvider`/`summarizationModel`, `modelPolicies[]`), default = latest routed target. A prior `<compacted-summary>` is consolidated, not copied.
- **Pruner** (`dsh-compaction-tool-result-pruner`): after a trigger qualifies, tool results over 8192 chars become 4096 head + marker + 1024 tail; originals stay in the log; if pruning relieves pressure the summary call is skipped.
- **Image offload** (`dsh-compaction-image-offload`): on `IMAGE_OFFLOAD_REQUIRED` from the DeepSeek adapter, oldest images are replaced with text placeholders naming the file path, logged as `image/offload`, and the request is retried without spending the retry budget.
- **Transaction**: `compaction/start` -> summary -> `compaction/summary` + replacement -> `compaction/end`. An unmatched start is a durable lock ("busy"). Failure of summarization keeps the over-budget history and proceeds (warn).
- **Does it preserve DeepSeek prefix cache?** Two separate facts:
  1. The *summarization call* replays system prompt, last routed tools, and shadowed messages byte-for-byte, then appends the instruction, so it is a prefix hit; only the instruction and output are uncached ("Summarization reuses the provider's warm prefix").
  2. The *replacement itself* breaks the cache from the first shadowed token (README "KV Cache effect: Replacing rather than append-only"). The retained tail has to be re-prefilled once. Only system+tools (and anything before the first non-system node) survive.
- Known limits: cannot shrink system prompt/tools; cannot split one indivisible huge unit; no model-facing compaction tool; the meter is heuristic when no provider usage is available.

### 1.4 Resume after process restart
- Yes. `ctx.agents.resume({sessionId,...})` / `agents[].resumeSessionId` / `agents[].sessionId` (resume-or-create with a stable id) in `dsh-agent-loop`. It does `persistence.open(id,'write')` (single-writer; second writer -> `SessionAlreadyOwnedError`; cross-process exclusion via `flock` on `session.lock`), reads the log, computes `interruptedTurnClosers` (synthetic `tool/result` errors `TOOL_NOT_STARTED` / `TOOL_OUTCOME_UNKNOWN`, any open `step/end`, `turn/end {interrupted}`), and appends them. The model is told, per recovered call, to retry only read-only/idempotent work and otherwise verify external state or ask.
- From a client: `ctx.sessionController.prompt()` "Admit one prompt after explicitly resuming its Session" (api-session-controller `commands.d.ts`); `resolveAgent(sessionId)` returns a live agent, resuming it if cold. `updateQueue` also resumes cold. aris already wraps this in its `SessionPort.agent(sessionId)`.
- Workspace placement: `dsh-workspace` (`ctx.workspaceRegistry`) groups sessions by cwd into projects; sessions with running turn/jobs/subagents/reminders cannot be hidden/archived without stopping them (archive admission).
- Idle eviction: I found no idle-timeout/eviction policy in `dsh-agent`, `dsh-agent-loop` or `dsh-api-session-controller`. Live agents persist until `AgentHandle.dispose()` or archive. **[inference]** a fleet of bots with long-lived live agents holds memory per agent; aris needs its own "dispose idle agent after N minutes, `resolveAgent` on next message" loop.

### 1.5 "Checkpoints"
- `dsh-session-checkpoint-policy` is a **durability policy, not a user-visible snapshot**: it `flush`es before the adapter stream is constructed, before a top-level tool body runs, and at each `agent/pre-step`. Fail-closed. It has no config. "Durable execution intent, not exactly-once effects": side-effecting tools should pass `exec.callId` as an idempotency key.
- Unfinished assistant streams are transient; a hard crash can lose a streaming reply that had no durable `assistant/message`/`assistant/attempt` yet.
- Known gap: shutting down the root context with an active agent can leave the final `turn/end` unsaved (agent-loop limitation "Root shutdown persistence").
- Do not confuse with aris' own `packages/aris-checkpoints` (file/workspace snapshots, per repo layout).

### 1.6 Query/search
- `dsh-session-query` (`ctx.sessionQuery`): `listSessions`, `readSession`, `filterSessions`, `filterEvents` (literal text scan), `readEvent`, `listEvents`, `readSurface`, `traceSession`, `traceEvent`, `readTitleSnapshots`; `dsh-session-query-sqlite` adds ranked FTS5 `searchSessions`/`searchEvents` with cursor pagination (derived index DB, single process owner, `openAt` startup/lazy/never). No caller authorization: "a model tool or UI must constrain which sessions its caller may inspect".
- `dsh-session-projection` (`ctx.sessionProjections`): synchronous unit folds over committed events produce client-visible JSON (goal, todos, inbox, tokenUsage, contextPressure, subagentCatalog, userQuestions...). Rebuilt from the log on restart; `session-projection-cache` persists rows. Useful for "what is this bot doing now" without opening the log.
- `dsh-experimental-session-search`, `session-inspector`, `session-titles-*` exist (not read in depth).

## 2. Turn model

### 2.1 Injecting input into a running turn
`Agent` (`dsh-agent` `lib/types/runtime-types.d.ts`), driver `ReactLoopAgent` (`dsh-agent-loop`, `src/agent.ts`, `src/inbox.ts`):

| Method | Semantics |
|---|---|
| `followup(msg)` | Queue an ordinary prompt as the sole message of its **own next turn**; wakes the driver (idle -> starts turn). Inbox list `nextTurn`. |
| `steer(msg)` | Next-step input. Running driver consumes it at its **next step boundary** (between model request / tool batch); idle driver starts a turn. A rejected step parks steering until next wake. Inbox list `nextStep`. |
| `inject(msg)` | Model-facing context for the next pre-step, **does not wake**; may miss a request whose pre-step already claimed its batch. |
| `send(msg, target, wakeup)` | General form of the above. |
| `cancel(cause, {keepInbox?})` | Aborts active turn or maintenance task; default also clears queued+steering inbox with a logged `canceled` splice; `keepInbox:true` aborts only the turn and preserves pending items. First cause wins. No step-only abort. No-op when idle. |
| `whenIdle()` | Resolves at whole-agent quiescence. |
| `runMaintenance(task)` | Idle-only non-turn task (used by `/compact`); waking input is held until it settles. |
| `status` | `'idle' | 'running'` (running includes waiting for an approval or an answer: archive-admission doc says "a turn waiting for an approval or an answer included"). |
| `inbox.nextTurn/nextStep/clear()` | Read/clear pending work. |

- Inbox mutations commit `agent/inbox/spliced` events (durable, replayable); notifications `agent/inbox/inserted|claimed|discarded`. Duplicate prompt retries with the same `requestId` return the original acceptance (session-controller `prompt`).
- `agent/turn-stopping` runs before an otherwise-complete turn closes; a listener can `steer` to keep it open. `agent/pre-step` can reject a step or replace the messages entering it. `agent/request-error` can request retry.
- Remote/UI path: `ctx.sessionController.prompt({requestId, sessionId, mode:'queue'|'steer', content, clientTimeZone})`, `updateQueue`, `cancel` (cancel via controller **retains pending inbox**, i.e. `keepInbox`), `session/control` stream, `follow`/`page` history streams.

### 2.2 Concurrent prompts to one session
- One agent drives one session; turns are strictly serial. Two `followup()`s become two turns in arrival order; a `steer()` while running joins the *current* turn at the next boundary; several steers claim together at one boundary. Persistence enforces a single writer per session (in-process claim + `flock`). `session.create` with the same id serializes by arrival order. No parallel turns per session.
- "Wake gap" hazards documented: a follow-up accepted after interrupt but before idle waits until another waking send (`dsh-subagent` limits); a settlement in the driver's retirement window can strand a notice (`dsh-tool-jobs` limits, "Steering has the same hole").
- aris today (`aris-channels/src/hub.ts` `submit`): running + owner + `busy:'steer'` -> `agent.steer`; `busy:'interrupt'` -> `cancel`+`followup`; non-owner while running -> cancel + followup (supersede). That is correct use of the API; the gaps below are about durability, not steering.

### 2.3 Interrupt
`agent.cancel({kind:'user'})` or `sessionController.cancel`. Cancellation is cooperative; streamed assistant text already delivered is finalized; undispatched tool calls get `ABORTED_BEFORE_DISPATCH` results; approvals/questions raced against the turn signal settle `cancelled`. Goal rounds: a cancel pauses the goal at next idle (`dsh-goal-round-driver`). `agent/turn-stopping` and `agent/pre-step` allow policy hooks (the loop has "No built-in turn budget"; cancel from those hooks to bound runaway turns).

## 3. Human waits

### 3.1 Approvals (`dsh-user-approval`, `ctx.userApproval`; also `dsh-authorization`)
- `ApprovalService.request({agent, tool, callId?, reason?, signal})` requires an **open turn** (throws "outside an open turn" otherwise), appends `approval/asked`, then `await this.decide(req, session)` -> dispatches the `approval/request` waterfall to composed answerers, raced against the turn signal; appends `approval/decided`. Outcomes: `allowed-once`, `rejected`, `cancelled`, `unavailable` (fail closed). Policy per session: `ask` | `never` (`approval/policy` event, `setPolicy`).
- **Mechanism: in-process awaited promise.** The turn, step, tool call, agent and session stay resident in memory, holding a slot, until an answerer returns. No timeout in the service itself (answerer-owned).
- **Daemon restart while waiting**: `approval/asked` is in the log, `approval/decided` is not; the tool has a `tool/call` but no result, so resume appends `TOOL_OUTCOME_UNKNOWN` and `turn/end {interrupted}`. The approval is silently dead; the model is told the outcome is unknown and to verify/ask. Limitation text: "a durable out-of-turn approval workflow is deferred", "Only one-shot grants exist" (no allow-always / grant store), "The request carries no tool arguments".
- Answerers are waterfall listeners; "a deployment composes one terminal answerer". The shipped Web answerer is browser-based (Remote Events routed per agent scope). aris has its own shared approval inbox (`ApprovalItem` in `aris-channels/hub.ts`, `arisApprovals` in `@aris/commander`) acting as that terminal answerer **[inference from file names]**.
- `dsh-experimental-auto-review`: an LLM reviewer answers instead of the human; shipped *off*, "can allow unsafe actions", no persistent grants; useful to reduce human waits but it is a policy choice, not a wait mechanism.

### 3.2 User questions (`dsh-user-questions` `ctx.userQuestions`, `dsh-tool-ask-user`)
- `ask()` is the same in-process await (legacy/blocking; `timeout:-1` also waits indefinitely).
- `askTimed()` / `ask_user_question {mode:'timed', timeout}` is the **one real release-and-resume path**: a `TimedQuestionWait` holds the model only until a deadline (Host clock; an answer UI that "claims" the wait via `attachWait` holds it while the user is editing). At the deadline the tool returns `{pending:true, callId}` and the model **continues independent work**; the question stays answerable. The `userQuestions` projection derives open/continued/settled questions from existing session events (tool call, result, reply). When the answer arrives later, the `answer` Remote method **steers it into the agent as a `user-question-reply` message** (kind/tool/callId); "Answering a closed Session resumes its root agent first". One queued reply per continued call (`REPLY_QUEUED`). Survives restart: "the question survives restart across clients through the projection"; if the owning process ended, the question is `continued` and the reply steers in. Gaps: a legacy/blocking call interrupted by restart cannot take a late answer; PTC (`run_code`) sub-call may lose its question; runtime-owned subagents cannot ask (`DELEGATED_CALLER`).
- Takeover (a human taking over a bot's thread) has no dsh primitive; practical form is `cancel({keepInbox:true})` + human messages as `followup` with a distinguishing `MessageSource` **[inference]**.

### 3.3 Net answer
Approvals hold memory and die on restart. Timed questions are the model for "pause, free the turn, resume exactly". See the gap table for how aris can give approvals the same shape.

## 5. Multi-user: Principal and remote access

- `dsh-typert-protocol`: `PrincipalMap` is merge-extensible; built-in `owner: {kind:'owner'}`. A driver declares additional entries (unique literal `kind`, JSON, **no credential**, safe to persist). `PeerScope.principal` is fixed by in-process Host code when a Peer is created (no wire field can set it); `PeerScope.interactions: 'answer'|'none'` decides whether a Peer may answer forwarded waterfalls (approvals/questions). `principalOf(this.ctx.invocation)` returns the non-owner principal or `undefined`; `session/prompt` records it on the durable `user-rpc` message source **only for non-owner callers**.
- `dsh-api-remote-access` (`ctx.remoteAccess: RemoteAccessService`): business packages define *roles* (action sets over a resource kind); `registerPolicy(kind, policy)` binds roles to resources per non-owner principal kind; `decide`, `allows`, `snapshotFor`, `follow`, `invalidate`. The Gateway checks before decoding arguments. `api-session-controller` registers the `session` resource kind (field `sessionId`; subagent address uses `childSessionId`; whether parent grant covers children is the policy's rule). `session/list|search|control` touch `global` resource and need a `global` role; results are filtered per principal. Non-owner `$events` get only broadcast frames whose `event:<name>` action is allowed.
- Gaps: non-owner **interaction participation (answering approvals/questions) is owner-only** ("Interaction participation ... is owner-only"); Connection Fetch routes (e.g. `/api/file`) return 403 to non-owners; a granted session leaks the owner's absolute paths and `home`; no built-in per-user message attribution beyond `MessageSource`/`principal` on the prompt; `session-query` has no authorization.
- aris fit **[inference]**: channel users (Telegram/Zalo/Lark guests vs owner) are better modeled in aris' own layer (`aris-channels` `roleOf`, `trust: owner|guest`, already present) and by tagging each inbound `UserMessage.source` with the sender; use dsh `Principal`+`registerPolicy` only if non-owner people connect through the dsh Web gateway directly.

## 6. Cache behaviour (DeepSeek prefix cache)

- Provider: `dsh-llm-deepseek` (route `deepseek-official`, default models `deepseek-flash` text+image and `deepseek-v4-pro` text, 1,000,000-token window). It reports cache-hit metrics into harness usage ("cache accounting maps DeepSeek's cache-hit metrics into harness usage"; "Cache-read usage is reported when available") and sends a stable anonymous user id and the session id. No explicit cache-control knobs; reuse is automatic prefix matching. The adapter also pins reasoning passback (every reasoned turn's chain of thought appended on later requests, so thinking tokens accumulate in the prefix).
- **Stability rules enforced by design** (README "KV Cache effect" sections across `dsh-session`, `dsh-agent-loop`, `dsh-system-prompt`, `dsh-compaction-*`):
  - History is append-only; every normal turn appends after the reusable prefix.
  - `request/header` (call config + tool schemas) is logged once per series and only rewritten on change; "unchanged steps, retries, and ordinary later turns inherit the latest header". A changed tool schema or tool *order* invalidates reuse from the first changed token (`dsh-system-prompt`: "Registration, restriction, or reordering may invalidate reuse").
  - Dynamic facts are kept **out of the system prompt**: `ctx.systemPrompt` separates *sections* (static prompt text) from *contexts* (dynamic runtime facts), and contexts become sourced user-role snapshots in history (`refreshContext(...)` after pre-step). So volatile data (time, bot state) should go through contexts, not sections.
  - `systemPromptUpdate: 'in-history'` (declared on the DeepSeek catalog entries): if the rendered prompt changes inside a continuing request series, the new prompt is **appended after the cached history** instead of rewriting node 0, preserving the prefix. Without it, a prompt change rewrites the head and loses reuse from token 0. An unchanged rendering produces no event.
  - A new "request series" (surface replacement/compaction, image-offload decision, plugin message change, `startsRequestSeries`, resume) writes a fresh header; prefix reuse restarts from the first changed token.
  - Image handling: Files ids vs inline base64, oldest-prefix removal in byte/count **quanta** with a "stepped high-watermark policy [that] avoids rewriting an old request prefix after every new image" (`imageOffloadByteQuantum` 64 MiB, `inlineImageOffloadByteQuantum` 10 MiB).
- **"Rebuild only when worth it"** is exactly the compaction design: compaction fires only above a pressure threshold (default 80% of W, bounded by W-O-65536), the pruner runs only when a trigger qualified ("a below-pressure conversation is never touched"), a summary must shrink its source or it is rejected, and image offload uses coarse quanta. `dsh-session` also pre-computes nothing destructive: shadowed events stay in the log. For a 1M window the first compaction triggers around 800k tokens (**[inference]** arithmetic: min(0.8*1M, 1M-O-65,536) with O the output cap), so cache invalidation from compaction is rare; per-turn cache health is dominated by not touching tools/system.
- Things that silently hurt cache **[inference from READMEs]**: toggling tools per turn, changing persona/variables, renaming execution-world paths (image descriptor text), route/model switches (different cache domain), `/compact` run casually, runtime-context snapshots that change every step (they append, so they cost tokens but not older prefix), and the pruner rewriting old tool results (it only runs inside a qualified compaction, so it shares that single invalidation).
- Metering: `dsh-token-meter` (`ctx.tokenMeter`, projections `tokenUsage`, `contextPressure`, `contextBreakdown`): deterministic, replays the log, reuses provider-reported usage only for an identical request envelope. Use `contextPressure` for a bot-level "approaching compaction" signal and `tokenUsage` for per-bot cost.
- Spill/retention (token hygiene, no cache impact if deterministic): `dsh-spill` (`ctx.spillStore` opaque locator), `dsh-spill-local` (session-scoped private files), `dsh-spill-policy` (`maxInlineTokens`: head/tail preview plus path for oversized tool text/images; omitting disables), `dsh-output-retention` (library `ItemRetainer`, `TextRetainer`, `formatRetentionNotice`). `dsh-repeat-tool-reminder` appends advisory nudges at 3/5/8 identical repeated tool calls (append-only, no cache effect; chains cleared by a new user message; per agent).

## 7. Voice (speech-to-text)
`dsh-experimental-speech-to-text` provides `ctx.speechToText` (named recognizers resolved per request); `dsh-experimental-speech-to-text-sensevoice` is a CPU provider (SenseVoiceSmall ONNX + Silero VAD via sherpa-onnx, no Python). Output is plain text, so a voice message from a channel becomes an ordinary `UserMessage`/`followup`/`steer`; nothing session-specific.  Client side: `dsh-experimental-voice-input-bundle`, `-client-ui-voice-input`, `-api-speech-to-text`. Not on the critical path for persistence.

## 8. Capability table: persistent bot thread

Legend: HAS = dsh provides it as-is; PARTLY = provides a primitive but a gap remains; MISSING = nothing usable.

| 2 | Durable, crash-safe log, restart resume | HAS | `dsh-session-persistence-jsonl` + `dsh-session-checkpoint-policy`; agent-loop `interruptedTurnClosers` | Mandatory to mount both rows in every aris profile. ## 9. Concrete recommendations for aris (ordered)

1. Pin the composition: `dsh-session`, `dsh-session-persistence-jsonl`, `dsh-session-checkpoint-policy`, `dsh-token-meter`, `dsh-compaction-tool-result-pruner`, `dsh-compaction-basic`, `dsh-compaction-image-offload`, `dsh-schedule`, `dsh-tool-schedule`, `dsh-tool-ask-user` (timed), `dsh-tool-jobs`+`dsh-jobs-local` (for in-turn background), `dsh-spill-*`, `dsh-session-query-sqlite` (check which are already in `aris-bundle`).
2. Add an aris "Bot Thread Manager" plugin owning: `bot -> sessionId`, serializer per bot, idle eviction, rollover, restart recovery (list sessions with unanswered inbox / pending approvals and re-notify), and a single outbound sink that posts results of any source (reply, schedule, job, subagent) to the channel.
3. Replace blocking approvals with a durable approval record plus follow-up resume (row 9); keep dsh's `unavailable`-fails-closed semantics as the safety net.
4. Make every background producer deliver through `resolveAgent(sessionId).followup(message)` with a `MessageSource` naming the producer and an idempotency id; never rely on `dsh-subagent` parent delivery or job notices across restarts.
5. Treat summarization as part of memory strategy: `aris-memory` writes facts to a durable store, compaction summary handles conversational state; choose a cheaper `summarizationModel` but expect cold cache for the retained tail after each checkpoint.
6. Add an integration test matrix: restart mid-approval, restart mid-tool, steer during tool batch, steer during approval wait (expected: sits in inbox until the awaiting tool returns **[inference]**), concurrent webhook retries with same `requestId`, compaction under load.

## 10. Caveats and what I did not verify
- I read READMEs and d.ts for most packages; compiled JS only for `dsh-user-approval` (confirmed `await this.decide(...)`, open-turn precondition, `approval/asked` and `approval/decided`).
- Not read in depth: `dsh-workflow`, `dsh-acp*`, `dsh-api-job-controller`, `dsh-session-projection-cache`, storage-domain internals, session-title/inspector packages, and `dsh-authorization` beyond summary.
- Behavior of `steer` while a turn is blocked in an approval await is inferred from `steer()` docs ("consumes it at its next step boundary") plus `status` staying `running`; I found no explicit statement.
- Idle-agent eviction absence is an absence-of-evidence finding from grep over READMEs and the d.ts of three packages.
- The arithmetic for compaction trigger with a 1M window assumes a typical output cap; actual O comes from the request envelope.
