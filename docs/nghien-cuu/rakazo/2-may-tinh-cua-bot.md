# Rakazo bot computers (sandboxes): research report

Source: shallow clone at commit beaed0c (Apache-2.0). Read-only; nothing was run. All paths are relative to the repo root unless noted. Statements marked **[inference]** are mine; everything else is read from the cited file.

## 0. Architecture in one paragraph

The agent ("Pi" runtime) runs in the Rakazo API/worker process, NOT in the sandbox (`docs/computer-runtime.md`). It calls ordinary built-in tools (`computer_observe`, `computer_act`, `shell`, `browser_*`, `request_takeover`, ...) which go through a provider interface, `SandboxProvider` (`packages/adapter-kit/src/interfaces.ts:97`). Providers: `docker` (local, via a "supervisor" service), `e2b`, `novita`, `daytona`, `createos`, `boat`, `boxd`, `railway`, `kubernetes`, `wuying`, `desktop` (dev-only host), `fake`, `none` (`packages/contracts/src/ids.ts:54`, `packages/adapters/src/sandbox-factory.ts`). A "computer" is a Linux box with a virtual X display, window manager, Chromium, VNC streamed through noVNC, plus a home directory that is checkpointed to Rakazo-owned storage. The model sees screenshots (so it needs a vision-capable model) and/or a text DOM snapshot of the page.

## 1. What is inside a computer image

Main image: `infra/sandboxes/computer/Dockerfile` (multi-stage; builder stage compiles `xcapture.c` into `librakazo-xcapture.so`).

- **OS**: `debian:bookworm-slim` pinned by digest. Runs as uid/gid 1000 (`rakazo`), `USER 1000:1000`, no root at runtime ("nothing can be installed at runtime" - comment in the Dockerfile). Works with a bind-mounted home of any host uid via `libnss-wrapper` and `user-env.sh`.
- **Display/desktop**: `Xvfb :1` 1280x800x24 (`infra/sandboxes/computer/start.sh`), `fluxbox` window manager (configs `fluxbox.init|apps|menu`), `xterm`, `xdotool`, `wmctrl`, `imagemagick`, `xclip/xsel`, dbus + `xdg-desktop-portal(-gtk)` (so the Chromium file chooser/uploads work), black background `#111113`.
- **Browser**: Chromium by default; `--build-arg BROWSER=brave` installs Brave instead (Brave Rewards/Wallet/Leo/VPN disabled by policy). A wrapper `rakazo-browser` launches it with a per-display profile under `~/.browser-profiles/` and a remote-debugging (CDP) port `9221 + display number` (`infra/sandboxes/computer/rakazo-browser`). Managed policy `browser-policy.json` disables the password manager and autofill (Rakazo keeps credentials itself).
- **Streaming**: `x11vnc` (view-only, loopback 5900) + `websockify` serving the noVNC web client on port 6080 with a token file (`start.sh`). Custom `embed.html`, `clipboard-bridge.js`, `mobile-keyboard.js` are layered on top of noVNC (`Dockerfile` COPY lines). For multi-bot Team computers there are extra per-bot displays and a shared token-protected gateway (see section 3 and `packages/core/src/node/desktop-runtime.ts`).
- **Control daemon**: `control.py` (Python stdlib HTTP server, port 7070, `POST /v1/desktop`, bearer token `RAKAZO_COMPUTER_CONTROL_TOKEN`, constant-time compare) accepts only an allowlist of `xdotool`/launch argv and returns a PNG screenshot captured through the C library (MIT-SHM + libpng) (`control.py`, `xcapture.c`).
- **Page-browser helper**: `rakazo-page-browser` (Python, stdlib, hand-rolled CDP websocket client) attaches to the visible Chromium on that display; `rakazo-focus-or-launch` focuses/launches apps.
- **Tooling for bots**: `curl git jq openssh-client unzip poppler-utils(pdftotext) pandoc python3 python3-openpyxl`, `uv`/`uvx` (pinned, sha256-verified), GitHub `gh` (pinned, sha256-verified), CJK + emoji fonts, locales (incl. zh_CN). No compilers ("heavier toolchains are a separate call"). Python and `uv tool install` installs persist in the home volume.
- **Terminal / files**: an xterm on the desktop; plus a separate browser terminal (PTY server, `packages/core/src/node/terminal-server.ts`) and a file browser in the web UI (`docs/computer-runtime.md` "Terminal and files").
- **Size**: not stated anywhere I found. **[inference]** a Debian + Xvfb + Chromium + fonts + pandoc image is likely on the order of 1.5-2.5 GB; do not rely on this. Runtime ceilings in section 6.
- **How built**: Docker `buildx` from the Dockerfile; published as `ghcr.io/elie222/rakazo/computer` (`docs/self-host-sandbox-providers.md`; `infra/compose/.env.images.example:78`). The supervisor can also build the image locally from the file list `COMPUTER_IMAGE_CONTEXT_FILES` in `infra/sandboxes/supervisor/src/computer-spec.ts`.
- **Other images**: `infra/sandboxes/desktop/Dockerfile` is a much smaller Debian with Xvfb/x11vnc/fluxbox (no noVNC, no browser) - appears to be a legacy/minimal variant. Remote providers do NOT use the Dockerfile: they take the provider's own desktop image and install missing tools at first boot via `PREPARE_LINUX_DESKTOP` (apt-get; `packages/adapters/src/linux-desktop.ts:399`) or a prebuilt template/snapshot: E2B template `rakazo-computer` (stock `desktop` at 2 vCPU/4 GB; `packages/adapters/src/e2b-template.ts`), Novita template, Boat snapshot `rakazo-computer-<hash>` built in the background (`boat-sandbox.ts`), boxd snapshot, Daytona `DAYTONA_SNAPSHOT`, CreateOS rootfs `desktop:1` (`docs/self-host-sandbox-providers.md`).
- Railway: own `infra/railway/Dockerfile` + `start.sh` for the app itself; computers are Railway sandboxes in a separate empty environment (`infra/railway/README.md`).

## 2. Lifecycle

Source of truth: `packages/adapters/src/computer-lifecycle.ts` (provision, execution leases, replace), `computer-idle.ts` (sleep), `computer-update.ts`, `docs/computer-runtime.md`, `docs/computer.md`. DB row: model `Computer` in `packages/db/prisma/schema.prisma:1344` (state `stopped|booting|running|suspended|error`, `providerRef`, `homeKey`, `homeRevision`, control/execution lease + fence fields).

- **Create / start**: lazy. A computer boots only when a run first uses a computer tool (`docs/self-host-sandbox-providers.md`). `provisionComputer` calls `SandboxProvider.provision` (returns a `ComputerRef` with the opaque `providerRef`), then `prepare`, then imports the latest saved home (`importWorkspace`). The DB `providerRef` is only "an acceleration path, not durable data"; if the machine is gone or the provider kind changed, a replacement is created and the home restored (`computer-runtime.md`, Daytona section). `restorePending` flag prevents saving from a half-restored machine (schema comment).
- **Sleep on idle**: `SANDBOX_IDLE_MS` default 600000 (10 min), min 30000, `0` disables (`computer-idle.ts:36,327`, `.env.example:212`). A sweeper runs every 10 min to queue idle checks (`IDLE_SWEEP_INTERVAL_MS`). Idle stop is skipped while a background process holds a marker (the shell tool wraps commands in `BACKGROUND_WORK_LAUNCH` so long-running jobs/CLI agents count as activity; probe in `computer-idle.ts` ~line 300). Providers that bill while running additionally stop at `COMPUTER_MAX_ACTIVE_MS` (default 2 h, `0` = off) unless a run, user control, or recent coding-agent CLI writes hold it (`self-host-sandbox-providers.md`). Docker and this-Mac computers are never capped. Idle shutdown "claims the computer before exporting" so a new bot cannot start mid-snapshot.
- **Wake**: next tool use, or opening the computer in the UI, re-provisions/resumes (`docs/computer.md`). Novita pauses (keeps memory); boxd suspends with memory; Boat archives and resumes the same sandbox id; E2B/Daytona/Kubernetes are treated as ephemeral and rely on the checkpoint.
- **Saved workspace ("snapshot")**: NOT a VM disk snapshot. "The disposable OS image is not a portable disk snapshot" (`computer-runtime.md` Persistence). The portable home (`/home/rakazo` on Docker; `/home/user/rakazo-home` on remote providers) is exported file-by-file and checkpointed into `AgentHomeStore` at run completion/failure, before explicit stop, and before idle suspension. Backends: `LocalAgentHomeStore` (`DATA_DIR/homes/<home-key>`, latest-only) or `ObjectAgentHomeStore` (S3-compatible; archive sealed with AES-256-GCM 64 KiB segments, per-home data key wrapped by the space content key; deleting the computer makes objects unreadable). Excludes caches, `node_modules`, `.venv`, `.next`, logs, core dumps; refuses homes over 5 GiB or 1M files (stays running unsaved, with a system note). Docker mounts the home directly (no copy). Kubernetes can optionally mount the API's PVC subpath (`KUBERNETES_SANDBOX_HOME_CLAIM`).
- **Persistence of browser sign-ins**: Chrome profiles live inside the home (`.browser-profiles/...`), so cookies/logins are checkpointed with it; remote providers quiesce browsers before export so profile DBs are consistent; transient browser caches are excluded but login state is kept (`computer-runtime.md`).
- **Stop / Update / Recover / Reset** (UI "More computer actions", `docs/computer.md`): Stop = shut down now; Update = save workspace + rebuild with the configured provider/image (`computer-update.ts`, `replaceComputer` mode `update`); Recover = recreate a broken computer (may fall back to last saved workspace); Reset = go back to last saved workspace (unsaved work lost). These are durable background jobs with a computer-wide reservation that blocks new leases/stop/takeover/idle; heartbeat 10 min, "Release computer" owner-only escape hatch (`computer/releaseInterrupted` RPC) (`computer-runtime.md` Computer maintenance). There is also auto-recovery once when a damaged system is detected (`autoRecoveredAt`, `computer-auto-recover.test.ts`).
- **Metering**: each running stretch is a `computer_runs` row (`endReason`: stopped/idle/active_limit/replaced/gone/deleted/reconciled); a monthly "allowance" prices billed providers at $0.20/h (`packages/adapters/src/sandbox-allowance.ts`).

## 3. Team vs Private computers

- DB: `Computer.scope` (`"team"` | `"dedicated"` = Private) and `scopeKey` unique (`packages/db/src/computers.ts:12-37`). Team key is `team:<spaceId>:<userId>` (one Team Computer per user per space), Private is per bot. Setting is Bot settings > Advanced > Computer (`docs/computer.md`). Quotas: `SANDBOX_MAX_COMPUTERS_PER_USER`, `SANDBOX_MAX_COMPUTERS_PER_SPACE`.
- **Team**: all Team bots share one OS user, workspace, installed tools. Each bot starts in `bots/<bot-id>/`; `shared/` for common work. "These folders organize work but are not security boundaries" (`computer-runtime.md`).
- **Per-bot screen on a shared machine**: each active bot gets its own X display (Docker: `:1`, then more; remote Linux providers start at `DISPLAY_START = 20` in `remote-desktop-sandbox.ts`), own Chrome process, and persistent profile keyed to bot identity (`chromium-screen-<N>` pattern in `rakazo-browser`; profile path file `/tmp/rakazo/browser-profile-<N>`). Profiles are never cloned/merged/deleted on release. Desktops start lazily; no default cap (`SANDBOX_TEAM_SCREEN_LIMIT` optional; over limit returns `MULTI_SCREEN_UNAVAILABLE`, shell/files still work; oldest idle screen may be torn down). All screens share one token-protected websockify gateway; each view/control capability points to a unique local Unix socket so a recycled display cannot be reached by an old connection.
- **Concurrency/fencing**: per-bot DB execution leases with fence counters (`ComputerExecutionLease`, `acquireComputerExecutionLease` in `computer-lifecycle.ts:815`); one driver per bot at a time; checkpoints defer while another bot holds a lease.
- Docs claim sign-ins carry over to other Team bots ("sites you sign in to are carried over", `docs/computer.md`) but `computer-runtime.md` says profiles are independent and never cloned. **[inference]** these are reconciled by the login vault (saved logins are per user/bot-level credentials, `docs/bot-secrets.md`), not by sharing cookies; treat the `computer.md` sentence as loosely worded. Also `bot-secrets.md` advises a Private Computer for bots that sign in to sites, because on Team computers other bots' runs do not scrub that bot's secrets.

## 4. How the agent controls the computer

Tool names (`packages/contracts/src/builtin-tools.ts:20-35`; handlers `packages/adapters/src/run-tools-computer.ts:228`):

| Tool | What it does | Path |
|---|---|---|
| `computer_observe` | Screenshot (PNG, as image tool-result) + frameId, cursor, active window | `sandbox.observe` -> control daemon `capture` |
| `computer_act` | Batch of up to 24 actions: click/move/down/up (+double), `type` (implemented as clipboard paste), key+modifiers, scroll (aimed, optional point), wait (<=5 s), focus app (+uri); optional settle_ms and observe | `parseComputerActions` in `computer-tools.ts`, `sandbox.act` |
| `browser_navigate`, `browser_snapshot`, `browser_act` | Text/DOM-ref control of the live visible Chromium: bounded page text + up to 80 interactive elements with refs; stale refs rejected; password values masked; `fill_secret` for saved logins | `sandbox.pageBrowser` -> `rakazo-page-browser` over CDP |
| `shell` | bash command, env injected, streamed output; long commands detach and report "still running" | `sandbox.execute` |
| `read_file`, `write_file`, `attach_file`, `list_files` | Workspace files; `attach_file` sends file to chat | provider file ops |
| `open_path`, `launch_app` | Open file/URL or focus-or-launch an app on the desktop | `sandbox.act` with `open`/`focus` |
| `request_takeover` | Ask the human to take over for passwords, 2FA, CAPTCHA, payment, passkeys | `packages/adapters/src/builtin-tools.ts:535` |

Notes:
- Browser automation is **not** Playwright/Puppeteer and **not** a hosted browser service ("No hosted browser service or API key is required", `computer-runtime.md`). It is a hand-written CDP client (`rakazo-page-browser`) attached to the same Chromium the user watches (CDP bound to container loopback only, port 9221+display). Fake/emulator browser (`BROWSER_PROVIDER=fake|emulator`, jsdom-based `page-browser-session.ts`) is test-only.
- Loop guards: identical consecutive frames omit image bytes; after 3 identical visual actions with no change, `computer_act` refuses and points to `browser_snapshot` (`computer-tools.ts`, `MAX_CONSECUTIVE_UNCHANGED_VISUAL_ACTIONS`). A failed browser action reports whether outcome is uncertain; never auto-replay.
- **Protocol worker -> sandbox**:
  - Docker: HTTP to the **supervisor** service (Hono app, `infra/sandboxes/supervisor/src/index.ts`) with `SANDBOX_SUPERVISOR_TOKEN`. Routes: `POST /computers`, `GET /computers/:id`, `/exec`, `/browser`, `/observe`, `/actions`, `/files` (GET/POST), `/screen`, `/screen-mode`, `/terminal`, `/input`, `/stop`, `DELETE /computers/:id` (lines 218-1134). The supervisor uses dockerode (`docker exec` for commands) and calls the in-container control daemon at port 7070 with a per-container random `RAKAZO_COMPUTER_CONTROL_TOKEN` (`control.py`; container create passes `controlToken: randomUUID()`). The adapter client is `packages/adapters/src/docker-sandbox.ts` (response size caps 16 MiB / 8 KiB errors, timeouts).
  - E2B/Novita: provider SDKs (`@e2b/desktop`, `novita-sandbox`) for command, files and port URLs; the shared `LinuxDesktop` class runs the same shell commands inside the VM (`linux-desktop.ts`, `remote-desktop-sandbox.ts`). So no resident Rakazo daemon is required on remote VMs **[inference]**: the "daemon" is the helper scripts installed/injected via shell, and the gateway is websockify. Daytona, Boat (SDK, protected port hosting), boxd, CreateOS, Railway (GraphQL + websocket), Kubernetes (`pods/exec`, tar streaming) each have their own transport but reuse the Linux desktop runtime.
  - The agent never gets direct network access to the sandbox's control plane; everything is mediated by API/worker.
- Shell redaction: secrets registered per run are scrubbed from command text and output (`run-tools-computer.ts` `redactSecrets`/`redactShellStreams`). Every computer action is recorded as a `computer.command` event for the Activity view.

## 5. How the user watches and takes control

- **Streaming tech**: noVNC (VNC over websockify) inside an iframe. Web: `apps/web/src/pages/shell/computer-panel.tsx` (iframe with `sandbox="allow-scripts allow-pointer-lock"` for `/novnc/` paths, `apps/web/src/lib/computer-screen.ts:78`), `computer-overlay.tsx`, `use-computer.tsx`. Desktop (Electron) hosts the same web UI; mobile has `apps/mobile/app/computer.tsx`. Wuying uses its own SDK page (`/wuying/screen.html`).
- **Capability URLs**: `computer.screenUrl` mints an encrypted, scope-bound capability (bot id, computer id, generations, control lease id; TTL 1 h; `packages/core/src/node/screen-capability.ts`, signed with `SCREEN_PROXY_SECRET`). The web service's proxy re-checks authority every ~1 s against `/api/internal/screen-target`; revocation drops the socket. Provider auth headers are sealed so they never reach browser URLs. View and control are separate revocable capabilities (view = x11vnc view-only; control = interactive transport).
- **Take control**: UI button -> RPC `computer.takeover` (`apps/api/src/routes/computer.ts:320`) creates a control lease (`controlHolder: user`, `controlLeaseId`, expiry `COMPUTER_TAKEOVER_TTL_MS` default 15 min, `computer-control.ts:9`) and a scheduled expiry job. Refused with 409 "Stop the bot first" if the bot has a live execution lease/run, unless run status is `waiting_takeover`. `computer.release` returns control; the header shows "You have control" / "Needs you".
- **Agent-requested handoff (CAPTCHA/OTP)**: `request_takeover` sets the run to `waiting_takeover`, UI shows "Needs you" with **I'm done** / **Skip**; on non-billed providers the computer stays awake 30 min (`TAKEOVER_IDLE_GRACE_MS`), billed providers restart the normal idle timer. When the user releases, the run resumes via `runContinueJob`. The tool description tells the model never to ask for protected values in chat.
- **Extras while in control**: interactive Shell tab (PTY server started in the computer, bound to the control token, runs as non-root workspace user, `connectTerminal`; Docker/E2B/Daytona/Boat; never for host computers), Files window with upload (needs control) and download (needs running computer), clipboard bridge, mobile keyboard shim. Screen load failures are classified via postMessage status from a shim injected into noVNC pages; 15 s silence shows Retry (`computer-runtime.md` "Screen connection diagnostics").

## 6. Provider abstraction, adding a provider, cost/resource limits

**Interface** (`packages/adapter-kit/src/interfaces.ts:97-206`), methods:
`describe`, `provision`, `prepare`, `execute` (AsyncIterable<ProcessEvent>), `connectScreen`, `observe`, `act`, `sendInput`, `listFiles`, `readFile`, `writeFile`, `exportWorkspace`, `importWorkspace`, `snapshot`, `stop`, `destroy` (required); optional: `billsWhileRunning`, `workspaceDirectories`, `environment`, `pageBrowser`, `provisionKind`, `isRunning`, `isStopped`, `hasMountedHome`, `cancelRunWork`, `inspectBackgroundWork`, `connectTerminal`, `setScreenControl`, `keepAlive`, `releaseScreen`. `describe()` returns capabilities such as `graphical, pty, snapshots, takeover`.

**Adding a provider** (derived from code **[inference on the exact checklist]**):
1. Implement `SandboxProvider` in `packages/adapters/src/<name>-sandbox.ts`. For a Linux VM with a command API, wrap `LinuxDesktop` (`linux-desktop.ts`) and/or the `remote-desktop-sandbox.ts` base, so displays, noVNC gateway, input, observe/act and terminal come for free; supply command exec, file I/O, and a way to get a URL for a port. Reuse `computer-support.ts` helpers (`computerObservation`, `normalizeWorkspacePath`) and `workspace-save-policy.ts`.
2. Add the kind to `SandboxKind` in `packages/contracts/src/ids.ts`, the options in `SandboxProviderOptions`, and a `case` in `createSandboxProvider` (`sandbox-factory.ts`) with a "missing key -> NoneSandboxProvider with message" guard.
3. Wire env vars (`packages/adapters/src/sandbox-provider-env.ts`, `.env.example`), docs row in `docs/self-host-sandbox-providers.md`, and add the provider to `sandbox-conformance.test.ts`, which runs a shared conformance suite (also `fake-sandbox.ts`, `*-sandbox.test-support.ts` for in-memory provider APIs).
4. Implement `billsWhileRunning` honestly so the uptime cap and allowance apply.
Note `packages/adapter-kit/src/registry.ts` exists for adapter registration generally; I did not verify whether sandboxes use it versus the switch in `sandbox-factory.ts`.

**Limits/cost**:
- Docker per-computer ceilings: `RAKAZO_COMPUTER_MEMORY` 2g (swap equal), `RAKAZO_COMPUTER_CPUS` 2, `RAKAZO_COMPUTER_PIDS_LIMIT` 2048, `ShmSize` 256 MiB (`infra/sandboxes/supervisor/src/computer-spec.ts`, `docs/self-host-docker-computers.md`). Count caps: `SANDBOX_MAX_COMPUTERS_PER_USER`, `_PER_SPACE`, `SANDBOX_TEAM_SCREEN_LIMIT`. Railway: 3 computers per user, idle stop 10 min (`infra/railway/README.md`).
- Remote sizes: E2B template 2 vCPU/4 GB; CreateOS shape `s-2vcpu-2gb`; Kubernetes CPU/memory limits via env; Boat 2 h TTL refreshed while active.
- Hourly price accounting: $0.20/h notional (`sandbox-allowance.ts`); per-org monthly allowance; run-time SQL examples in docs.
- Command timeout bounded (`boundedSandboxCommandTimeoutMs`); host bridge payload caps 12 MiB, files 8 MiB (`host-computer-protocol.ts`).

## 7. Network/security isolation, secrets, restricted network

- **Container hardening** (Docker): `CapDrop: ["ALL"]`, `no-new-privileges`, non-root uid 1000, `/usr/share/novnc` read-only, resource limits, dedicated per-bot bridge network named `rakazo-c...` (`computer-spec.ts:610-625`, `computerNetworkNameFor`). No `Privileged`. Supervisor holds the Docker socket, stays on an internal network, is never published; token `SANDBOX_SUPERVISOR_TOKEN` distinct from other secrets (`self-host-docker-computers.md`). Root filesystem is not read-only for the main computer (only the egress probe uses `ReadonlyRootfs`) - observed.
- **Egress**: `SANDBOX_COMPUTER_EGRESS=restricted|open|auto`. Restricted = public internet allowed but blocks Docker host, LAN, link-local/cloud metadata (169.254.169.254), via host iptables in `DOCKER-USER` + `INPUT` rules matching `rakazo-c*` bridge names (`infra/compose/restrict-computer-egress.sh`, installed by `install-images.sh`). Supervisor probes enforcement before starting (`egress-probe.ts`) and refuses to start computers if rules are missing (in `restricted`). Linux Docker Engine with iptables only; macOS/Windows/Docker Desktop/rootless fall back to `open`. Optional `SANDBOX_COMPUTER_DNS`. Shared host folders via `SANDBOX_COMPUTER_MOUNTS` (ro by default, deployment-wide, denied sources list).
- **"Restricted network" doc** (`docs/self-host-restricted-network.md`) is actually about installing behind blocked GitHub/registries (mirrors, `--offline`, image overrides), not sandbox egress. The egress feature is in the Docker computers doc.
- **Screen isolation**: capability tokens bound to bot/computer/generation/lease; unique Unix sockets per display; CDP loopback-only; Team bots share the OS user so lease fencing "coordinates tool calls, not mutually untrusted processes"; "use separate computers when workloads require isolation" (`computer-runtime.md`).
- **Kubernetes**: pod uid 1000, no service-account token, no service links, optional `runtimeClassName` (kata/gVisor), recommended NetworkPolicy (`self-host-sandbox-providers.md`). **boxd**: microVM, no boxd credentials inside. **Railway**: computers in a separate empty environment unable to reach app DB network. **Boat**: always `noEnv: true` so no account env leaks in. **Wuying**: all bots/spaces share one Windows desktop - explicitly "trusted deployment only".
- **Secrets**:
  - Vault: `vault_credentials` in Postgres, AES-256-GCM with `ENCRYPTION_KEY` (`docs/bot-secrets.md`). The model has no read tool. `secret_request` makes the *backend* do the authenticated HTTP call (origin-pinned, SSRF policy, 30 s, 1 MB, redaction), so the sandbox never sees the value.
  - **Command variables** (`auth: command`): injected as env vars on every `shell` call (loaded fresh per command by `shellCommandEnvironment`, `run-tools-computer.ts`), redacted from output in plain/base64/URL-encoded forms; reserved names (LD_*, GIT_CONFIG_*, NPM_CONFIG_*, RAKAZO_*...). The doc is explicit that the bot's shell can read them.
  - **Website logins** (`auth: login`): `browser_act fill_secret` types into the page only if the page origin still equals the saved HTTPS origin; value sent to the computer over stdin, not argv; hidden-field values scrubbed from tool results; snapshots never show filled values. Doc admits anything that can read the browser (shell via CDP port) could extract it.
  - Host-side secrets are not passed to desktop provider commands (minimal shell env). Remote provider API keys are server-only (`SandboxProviderOptions` in the API/worker).
  - Self-host secret storage alternatives: `docs/self-host-secrets.md`, `docs/infisical-secrets.md` (not read in detail).

## 8. "Use your own computer" mode (desktop app)

Two related mechanisms exist, both Electron-side (`apps/desktop/src/host-computer.ts`, `host-screen.ts`) with server-side code in `packages/adapters`.

**A. Local stack bridge ("Use this Mac"/"Use this computer")** - when the app runs its own local Docker Rakazo stack:
- Electron starts an HTTP server (`startHostComputerServer`, `packages/adapters/src/host-computer-server.ts`) on `0.0.0.0:<port>`, reached by the Docker backend at `http://host.docker.internal:<port>` (`host-computer.ts:connection`). Single route `POST /computer`, bearer token (32 random bytes hex, stored 0600 in userData; compared with `timingSafeEqual`), rejects any request with an `Origin` header, 403 until the user grants consent, 429 when busy, 12 MiB body cap, 30 s request timeout, NDJSON frame streaming.
- Consent: native dialog "Allow bots to use this computer?"; consent file stores the token, so changing the token invalidates consent. "Revoke Local Computer Access" disables the server immediately and aborts in-flight operations (`grant`/`revoke`/`activate` in `host-computer.ts`).
- Request vocabulary (`host-computer-protocol.ts`): provision, prepare, execute (argv, cwd, env, timeout), listFiles/readFile/writeFile, exportWorkspace, snapshot, stop, destroy, environment, plus `screenObserve`/`screenAct`. Workspaces live under `<userData>/computers`; file reads/exports capped at 8 MiB; commands run as the OS user via native shell (`native-shell.ts`, PowerShell on Windows). No graphical screen control for this provider ("Graphical screen control is unavailable").
- Safety: per `docs/desktop-app.md` WARNING - with **Use this Mac** "bots can run commands without asking"; do not use on a shared server. `SANDBOX_PROVIDER=desktop` (host exec on API host) is refused unless `NODE_ENV` is development/test (`assertHostCommandsAllowed`, `sandbox-factory.ts`).

**B. User-device tools (any server, including Cloud)** - Settings > General > Computers > "Let bots use this computer" (`docs/computer.md`, `docs/desktop-app.md`):
- Desktop app opens an outbound authenticated websocket to the server (`packages/adapters/src/user-device-gateway.ts`, `user-device-protocol.ts`; up to 10 devices per user, 25 s ping, token hashed with SHA-256 at rest, forwarding between API/worker processes via an HMAC-derived internal secret). Server sends the same `HostComputerRequest` messages down that socket; frames come back tagged by request id. Never retried after a lost response.
- Tools: `user_computer_shell`, `user_computer_observe`, `user_computer_act` (`run-tools-user-computer.ts`). Only available in runs started by the bot owner in person (trigger `user` or `follow_up`, not routines, webhooks, channels, other bots) - `userComputerOwner()`.
- Approval gate `userComputerGate`: asks before first command in a space and before each app is first used, in EVERY approval mode, until the user picks "Allow in this space"; Block rules still deny; approval is tied to the device pairing time (re-pairing re-asks); screen control is approved per app name (sanitized).

## 9. Takeaways for reuse

1. The cleanest idea is the provider contract + portable home: OS image is disposable, workspace (files + Chrome profile) is the durable unit, checkpointed encrypted. This makes provider migration and "sleep to zero" cheap.
2. One shared Linux desktop runtime for all VM-style providers (`linux-desktop.ts`) keeps per-provider code small.
3. Dual-channel browser control: text/DOM refs via CDP for cheap, reliable steps; screenshots + xdotool as fallback and for non-web apps; explicit loop guards and uncertain-outcome semantics.
4. Human handoff is first-class: separate view/control capabilities, lease + fence in Postgres, `waiting_takeover` run state, grace timer.
5. Security is layered but honest: Team computers are not isolated between bots; command variables are readable by the bot; Docker egress restriction requires host iptables.
6. Gaps/unknowns: image size not documented; I did not read the per-provider adapters (Daytona/CreateOS/Railway/boxd) in depth, `packages/db` RLS details, or web UI code beyond the iframe/takeover hooks.
