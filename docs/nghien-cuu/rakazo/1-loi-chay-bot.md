# Rakazo agent runtime: how it actually works

Source: commit beaed0c, read-only. Paths are relative to the repo root (`.../rakazo-src/repo/`). Statements marked **(inferred)** are my reading between files, not an explicit statement in code or docs. Nothing was executed.

## 0. Architecture in one paragraph

Rakazo is a TypeScript monorepo (pnpm/turbo). Product is "persistent AI teammates": each bot has one continuous chat thread, instructions, memory, and a persistent computer (sandbox). The agent loop is NOT custom: it is the third-party **Pi** library (`@earendil-works/pi-agent-core` + `@earendil-works/pi-ai`, pinned 1.3.0, see root/`packages/adapters/package.json` grep), wrapped by `packages/adapters/src/pi-runtime.ts`. Nearly all runtime logic lives in `packages/adapters/src/` (~33k lines non-test in the files I counted), NOT in `packages/core` (which is pure helpers: state machine, approval rules, prompt formatters, UI helpers) or `packages/memory` (a 179-line Postgres markdown store). Persistence is Postgres via Prisma (`packages/db/prisma/schema.prisma`). The queue is Graphile Worker plus a newer in-process direct dispatch. `VISION.md` is the product constitution.

## 1. Bot model, threads, spaces, groups

### Bot (`packages/db/prisma/schema.prisma`, `model Bot`, line ~640)
Fields: `spaceId`, `userId` (owner), `name`, `description` (the public "How other bots see it" blurb), `instructions` + `instructionHistory` (JSON, restorable versions), avatar/color/section/pin/position/archivedAt, `parentBotId` + `spawnKey` (bots created by other bots; unique per space, used as an idempotency key), `memoryScope` (isolated|shared override), `computerId` + `computerSwitching` (each bot is attached to a `Computer`; mode `team` shared or `dedicated`/Private, `ComputerModeSchema` in `packages/contracts/src/domain.ts`), voice (`voiceId`, `autoSpeak`), model override (`modelProvider`, `modelId`, `thinkingLevel`), `disabledBuiltinTools: String[]`, `webhookSecretId`, team-chat flags (`teamChatAmbientEnabled`, `teamChatRules`), `crossSpaceCommunication`, `fleetManagement` (can manage bots it created; note schema default is true but `docs/fleet-management.md` says "off by default" - conflict, unresolved), `notifyOnFinish`.
So a "teammate" = row + 1 Thread + AgentHome (files) + MemoryDocuments + Routines + ScratchpadItems ("Open work") + TaughtSkills + optional BotSecrets/BotMcpServer links. Doc: `docs/bots-and-chats.md`.

### Threads / messages / events
- `Thread` (`schema.prisma` ~775): exactly one per bot (`botId @unique`), or one per `ChatGroup` (`groupId @unique`), or one per `ExternalConversation` (Slack/Telegram/etc. channel). Holds `nextMessageSeq`, `nextEventSeq`, and compaction state: `historyCompactedUpToSeq`, `historyCompactionSummary`, `historyCompactionGeneration`. `VISION.md`: "One bot has one continuous visible thread because continuity is part of its identity, while internal runs and attempts remain implementation detail."
- `Message` (`blocks: Json` typed `MessageBlock`s - text, cards, ask/approval cards, `bot_message_sent`, etc.; `seq`; `clientNonce` dedupe; `searchTokens Int[]` blind-index for encrypted search). `Event` is an ordered per-thread realtime log (`type`, `payload`, `runId`).
- Content is encrypted at rest with per-space keys (`SpaceKey`, `docs/content-encryption.md`, `packages/db/src/content-crypto.ts`).

### Spaces (`docs/spaces.md`, `model Space`)
Authorization boundary: bots, chats, memory, computers, connections, saved credentials, skills a bot saves. Models/voice/approvals/vault are account defaults with per-space override (`SpaceSettingOverride`, `SpaceModelRoleChoice`, `SpaceModelPreference`). Skills/MCP/plugins are owned by the user and made available across spaces via `allSpaces` or `AgentSkillSpace`/`McpServerSpace`/`CapabilityInstallSpace` join tables. Cross-space bot messaging is opt-in per bot (`packages/db/src/cross-space-communication.ts`).

### Groups (`docs/groups.md`, `ChatGroup`, `ChatGroupMember`)
2-10 bots in one chat; each keeps own memory/computer/instructions, shares only the conversation. No mention -> first bot answers and may bring in others; `@name` wakes one; `@everyone` wakes all (`packages/core/src/group-mentions.ts`, `group-handoff` in adapters). Handoff tool `handoff_to_bot` appends a visible handoff and starts the target bot asynchronously (`packages/adapters/src/group-handoff.ts`; hop-limited, see section 3).

## 2. The run loop

### 2.1 What "Pi" is
Pi = the open-source coding-agent harness libraries `@earendil-works/pi-agent-core` (the `Agent` class: loop, tool execution, steering/follow-up queues, abort) and `@earendil-works/pi-ai` (provider-neutral streaming client + model catalog + OAuth/credential store) and `@earendil-works/pi-telemetry`. Rakazo imports `Agent` and `validateToolArguments` (`packages/adapters/src/pi-runtime.ts` lines 1-10) and `builtinModels` from `@earendil-works/pi-ai/providers/all` (`pi-models.ts`). I did not read Pi's source (not in the clone); its behavior is inferred from how Rakazo calls it. The runtime is registered behind an `AgentRuntime` interface (`packages/adapter-kit/src/interfaces.ts`); `PiAgentRuntime.describe()` returns `id:"pi"`; a `scripted-runtime.ts` implements the same interface for offline tests (`AGENT_RUNTIME=scripted`).

### 2.2 Providers, models, credentials
- Providers = whatever Pi's catalog ships (OpenAI, Anthropic, Google, OpenRouter, Azure, Groq, Codex/ChatGPT subscription, Claude subscription, etc.), plus a registered **local provider** (`pi-local-provider.ts`, env `RAKAZO_LOCAL_MODELS`) and a generic **OpenAI-compatible** provider (`pi-openai-compatible-provider.ts`; Chat Completions default, `apiProtocol:"responses"` option, per `docs/models.md`). A live catalog probe exists (`pi-live-catalog.ts`). Recommended default in `pi-models.ts`: `gpt-6-luna` for openai/openai-codex. Cloudflare AI Gateway supported (`cloudflare-ai-gateway.ts`).
- Credentials: stored per user as `UserModelCredential` (provider, label, `secretId` -> encrypted `Secret`) (`schema.prisma` ~552). Per-run, the executor resolves one into `AgentRunModel` (`apiKey` or `oauth`); `pi-runtime-models.ts` `resolveRuntimeModel` builds a request-scoped Pi `CredentialStore` (`PiRuntimeCredentialStore` in `pi-credentials.ts`) because Pi's default in-memory store cannot see Rakazo's encrypted DB; OAuth refreshes are serialized and persisted back encrypted. API key is passed through Pi's `getApiKey` callback (`pi-runtime.ts` Agent construction). Subscription sign-in (ChatGPT/Claude) via `pi-oauth.ts`, `pi-anthropic-oauth.ts`; retired/revoked tokens raise `RetiredModelCredentialError`. Hosted "Rakazo credits" path: `ModelCreditAccount/Entry/Lot` tables, `model-credit-observer.ts`.
- Role-based model choice: main model, ordered fallbacks, a separate **approval model** (`model-roles.ts`, `packages/contracts/src/model-roles.ts`, `docs/models.md`). Per-bot and per-routine model/thinking override. Thinking levels Minimal..Max mapped via `thinkingLevelFor` (`pi-runtime-models.ts`).
- Fallback: `fallbackAwareModelStream` (`pi-runtime-fallback.ts`, 833 lines) advances to the next model on transient/limit/credential failure, records `backupOutcomes`, re-sizes context policy on switch (`onSwitch`), and strips thinking signatures when changing models. Idle-stream watchdog 180 s, header timeout 120 s, connect 30 s, default 1 retry (`pi-runtime-limits.ts`); "Active model streams have no new duration limit" (`docs/run-execution.md`).

### 2.3 One turn, concretely (`PiAgentRuntime.runEvents`, `pi-runtime.ts`)
1. Resolve model + key; build `ToolHost` and `toAgentTools(request.tools, host)` (`pi-runtime-tools.ts`).
2. `request.claimSteering([])` pulls any user messages that arrived while queued; history built by `toHistory` or restored from a **turn checkpoint** (below).
3. System prompt = `request.instructions` (assembled by executor, `run-instructions.ts`, `run-context.ts`, includes current time, bot directory, computer guidance, skills catalog, memory, compacted summary) or a default.
4. `new Agent({ streamFn, getApiKey, steeringMode:"all", finishTurn, prepareNextTurnWithContext, initialState })`. `streamFn` wraps `reliableModelStream` -> `observedPiStream` (usage/telemetry) with the fallback layer.
5. `agent.subscribe(...)` translates Pi events (`message_start/update/end`, `tool_execution_start/end`, `turn_end`) into Rakazo `AgentRuntimeEvent`s pushed on an async queue: `text` deltas (streamed), `progress` (human tool-activity line from `describeToolActivity`), `thinking`, `turn`, `steered`, `subagent`, `done`. Executor consumes the queue and persists blocks/events, which clients follow over realtime.
6. Loop-quirk handling inside `pi-runtime.ts`: up to 3 "silent tool continuation" follow-ups when a model returns EOS right after a tool result (`MAX_SILENT_TOOL_CONTINUATIONS`); automated continuation prompts when a reply is cut by connection drop or output limit, with overlap-dedupe on the join (`cutReplyAtLimitPrompt`, `continuationRepeat`); per-run self-recovery cap. Automated user-role prompts are labeled (`automated-messages.ts`) so models do not mistake them for the user.
7. Tool-call safety: `ToolCallBudget` per run; consecutive-identical-call guard (6 identical, or 25 shape-similar calls -> stop with a "got stuck" message, `tool-loop.ts`); `pi-tool-call-guard.ts`; parameter coercion (`pi-runtime-tool-parameters.ts`, `openai-tool-parameters.ts`); result text clipped to 12,000 chars (`TOOL_RESULT_TEXT_LIMIT`).

### 2.4 Steering, interruption
- Messages sent while a run is active become `SteeringMessage` rows (`schema.prisma` ~938) and are injected into the live agent at the next turn boundary via `agent.steer(...)` (`prepareNextTurnWithContext`), emitting a `steered` event. `docs/run-execution.md`: "A message sent while a run is going steers that run instead of waiting." Routine/webhook/bot_message/created/tickets runs are non-conversational and don't take user steering (`packages/core/src/run-state.ts`).
- Stop: `PiAgentRuntime.abort(runId)` and `AbortSignal`; `agent.abort()` also aborts nested subagents. Cancelled is a terminal state. Aborting a quiet model stream settles immediately (tests: `pi-runtime-cancellation.test.ts`).
- Background shells: finished background shell output is fed back as a follow-up user message (`shell-command-stream.ts`, `finishTurn`).

### 2.5 Run state machine and durability
- `Run.status`: queued -> leased -> running -> {waiting_input, waiting_takeover, completed, failed, cancelled}; waiting_* -> queued/leased; failed -> queued (retry). Enforced by `assertTransition` (`packages/core/src/run-state.ts`). Triggers (`packages/contracts/src/runs.ts`): user, routine, resume, follow_up, reaction, call_end, spawn, skill, bot_message, webhook, messaging, cloud_agent, purchase, created, tickets.
- Rows: `Task` (prompt) -> `Run` -> `Attempt` (each execution try, with `fence`). Lease fields on Run: `leaseOwner`, `leaseFence`, `leaseExpiresAt`; heartbeat renewal every call renews a 5-minute lease (`renewRunLease`, `run-lifecycle.ts`); `nextFence` / fenced writes ensure one executor wins (`finalizeRun` takes `leaseOwner`+`leaseFence`). Setup failures retry up to 8 in a row (`RUN_SETUP_FAILURE_LIMIT`).
- **Queue / dispatch** (`docs/run-execution.md`, `wakeup.ts`, `run-wakeup.ts`, `run-execution.ts`): new design = no queue on the hot path. API process that commits a message calls `RunStarter` which starts the run immediately as an independent task in the same process; HTTP returns at once. A process shutting down or low on memory publishes the run id on the realtime connection and a worker takes it (`runs:ready` topic). Workers also scan for runnable rows at startup and every 5 s (expired lease, lost start). Admission control is by free physical memory and V8 heap headroom (`RunExecutionHost.admissionMemory`), not by a concurrency count. **Graphile Worker** (`graphile-worker` 0.17.3; `GraphileJobPublisher` in `wakeup.ts`) is retained for scheduled/maintenance jobs; typed payloads in `packages/adapter-kit/src/background-jobs.ts`: `run.continue`, `routine.wakeup`, `routine.retry`, `computer.update/sleep/control-expire`, `skill.teaching-expire`, `call.expire`, `history.compact`, `messaging.deliver`, `cloud_agent.poll`, `purchase.poll`, `push.receipt`, etc. Legacy `run.continue` deliveries still drained for rolling upgrades. `apps/worker/src/index.ts` (448 lines) boots it; `job-reconciler.ts` runs a leader-locked (advisory lock) reconciliation every 30 s that re-publishes lost jobs and abandoned locks. Embedded installs can use a memory job driver.
- One run per bot computer at a time; background runs needing a busy computer stay queued and the releasing run starts the next (`computer-lifecycle.ts`, `ComputerExecutionLease`).
- **Resumability / long runs**: Human waits (approval, `ask_user`, `request_takeover`, `request_secret`) end the agent loop and release compute. Before pausing, executor stores a versioned **turn checkpoint** (full Pi message transcript, system prompt, pending tool-call id, sequential/parallel mode) in an `ExternalEffect` row, encrypted like messages (`turn-checkpoint.ts`, `serializeTurnCheckpoint`, `host.captureCheckpoint` in `pi-runtime.ts`; `docs/agent-verification.md` "Paused turn continuity"). Next attempt restores the original prompt and provider prefix, appends the answer under the original tool-call ID, and re-validates approved calls (canonical args, idempotency) before another model request. Main-tool batches run sequentially so a pause captures completed preceding calls. Checkpoints cover human waits only; recovery of an interrupted (crashed) attempt is "a separate concern" - on crash the attempt is re-run, with `ExternalEffect` idempotency keys preventing duplicate side effects (`run-effects.ts`, `approval-effect.ts`, `uncertainEffectResult`). Stuck-work policy: remind at 4 h, auto-cancel at 24 h; takeover waits expire at 30 min (`packages/core/src/stuck-work.ts`, `stuck-work.ts`).
- Observability: structured log events `run.execution_started/first_response/finished`, `run.queue_delayed`, admission events (documented with an Axiom alert query in `docs/run-execution.md`). Pi session JSONL recorder optional (`pi-session.ts`), OTEL via `pi-telemetry*.ts`.

### 2.6 Context management and compaction
Two independent layers:
1. **Per-run, deterministic, no LLM** (`runtime-context.ts` 743 lines, `context-selection.ts` 764, `context-pruning.ts`): each model call is prepared by `contextPolicy.prepareContext`. Keeps current request, steering, approvals and constraints "protected"; keeps tool results whole newest-first within 3/4 of the available input budget (min last 3 results); older results shortened to ~1 KB; stale screenshots/page snapshots pruned; images capped; and a **cache-aware rebuild economics rule** - `rebuildPaysOff()` only rebuilds the prefix when stale tokens exceed ~5*sqrt(rebuilt size * growth), because a rebuild breaks the provider prompt cache (comments cite ~1.25x write / 0.1x read pricing). Between rebuilds the sent transcript stays byte-identical so caching works. Cache retention modes: `pi-cache-retention.ts`, `pi-live-cache.ts`. If required context exceeds the window: `ContextBudgetError`. Principle in `docs/context-and-evals-tasks.md`: "Cache expiry alone must never trigger paid compaction".
2. **Cross-run thread history** (`history-compaction.ts`): window of 50 recent messages (200 legacy) is sent verbatim; once uncompacted >= window+batch (50), a `history.compact` Graphile job summarizes the next 50-message batch via an LLM into `Thread.historyCompactionSummary` (max 20k chars; 40k-char transcript cap; 2-8 min adaptive timeout). The summary is injected as an explicitly "untrusted historical data" block (`formatCompactedSummary`). Used only if the tail after the cursor is contiguous, else falls back to the legacy window. With a semantic-memory provider, "recalled" memories (max 5) are injected as `<recalled_memory>` and the verbatim window shrinks to 50.
3. **Retrieval tools** let the bot pull exact originals: `search_history` (literal keyword, scoped this_chat / my_chats, paginated, max 5 hits) and `read_history` (around a message, with linked run outcomes/artifacts) - `builtin-tools.ts` ~900-1000, `run-tools-memory.ts`. Cross-chat search is only allowed for direct human app runs and is revoked if outside text entered the run.

## 3. Tools, delegation, verification

### 3.1 Built-in tool list (`packages/contracts/src/builtin-tools.ts` `BUILTIN_TOOL_NAMES`; schemas in `packages/adapters/src/builtin-tools.ts`)

- Files/shell: `list_files`, `read_file`, `write_file`, `attach_file`, `shell`.
- User's own computer (desktop app host): `user_computer_shell`, `user_computer_observe`, `user_computer_act`.
- Web: `web_search`, `web_fetch` (SSRF-guarded, `web-ssrf.ts`; providers Parallel/Keenable/keyless).
- Human interaction: `ask_user`, `message_user`, `connect_app`, `call_user`, `end_call`.
- Secrets/payments: `request_secret`, `generate_secret`, `list_secrets`, `secret_request`, `forget_secret`, `request_purchase`, `purchase_status`, `paid_request`.
- Media/viz: `generate_image`, `generate_video`, `render_plot`.
- Memory/history: `remember`, `save_shared_memory`, `save_memory`, `recall_memory`, `forget_memory`, `search_history`, `read_history`.
- Planning/work: `scratchpad_list/add/update/complete/remove` ("Open work"), `task_catalog`, `board_tickets`, `ticket_get/create/update/comment` (a per-space kanban board where bots are assignees; trigger `tickets`), `schedule_create/list/update/cancel` (routines).
- Skills: `skill_read`, `skill_create`, `skill_update`, `skill_delete`.
- Delegation: `run_subagent`, `message_bot`, `handoff_to_bot`, `spawn_bot`, `create_space`, `update_bot`; fleet: `list_fleet`, `create_group`, `update_group`, `organize_bot`, `set_child_instructions`, `set_child_bot_model`, `create_child_routine`, `archive_bot`.
- External agents: `cloud_agent_launch/status/reply/cancel` (Cursor-style cloud coding agents, `cursor-cloud-agent.ts`, `CloudAgent` table, polled by `cloud_agent.poll`), `connect_agent`, `respond_agent_connection`, `message_agent` (bot-to-other-person's-bot over a messaging surface), `add_mcp_server`, `update_preferences`.
- Connectors are separate: MCP servers (`mcp-connector.ts`, `remote-mcp.ts`), Composio and Pipedream (`composio-connector.ts`, `pipedream-connector.ts`), GraphQL/HTTP "installed APIs", plugin-installed connectors. They are exposed via a **lazy tool catalog** (`lazy-tool-catalog.ts`: above `DIRECT_TOOL_LIMIT=20` tools, the bot gets `__catalog_search/__catalog_load/__catalog_execute` wrappers instead of every schema) - good context hygiene.
- Per-bot `disabledBuiltinTools` removes any of these (`disabledBuiltinToolSet`). Selection per run: `run-tool-selection.ts`. Fleet tools are hidden from runs not directly started by the owner (`docs/fleet-management.md`).

### 3.2 Delegation
- **Subagents** (`run_subagent`; `pi-runtime-subagent.ts`): a nested Pi `Agent` created inside the turn, depth capped at 1 ("Subagents cannot nest further"), max 4 parallel (`MAX_PARALLEL_SUBAGENTS`, gate), same tools minus `DELEGATION_TOOL_NAMES` (no delegation, no fleet tools), optional different model (`model_provider`+`model_id` must be connected), own context policy and fallback chain, result clipped and returned as the tool result; progress shown as a card (`subagent` event: running/completed/failed). No thread, no memory, no computer of its own (shares the host's).
- **Peer bots** (`message_bot`, `bots` in same space unless cross-space allowed): async - writes a `bot_message_sent` block in sender thread and a message in the recipient thread and enqueues a run with trigger `bot_message` (`bot-messages.ts`, `packages/core/src/bot-messages.ts`). Intent enum request|result|question|status|fyi. **Hop limit** `BOT_MESSAGE_MAX_HOPS` default 6 prevents ping-pong loops; outcomes of delegated runs are auto-returned to the requester (`returnBotMessageOutcome`, `Run.botOutcomeReturnedAt`; failure returns "Could not complete the delegated request"). Bots pick whom to ask from a roster rendered into the prompt (`renderBotDirectory`, capped at 40, `BOT_DIRECTORY_LIMIT`) built from each bot's `description`.
- **Groups**: `handoff_to_bot` transfers a distinct stage to another member (same hop machinery), mentions fan out.
- **Bot spawning**: `spawn_bot` creates a full bot with idempotent `spawnKey`; fleet tools let a parent rewrite child instructions/models (versioned, with expected-version check per `docs/fleet-management.md`), approval-gated (`set_child_instructions`, `set_child_bot_model` are in `EXPLICIT_APPROVAL_BUILTIN_TOOLS`).
- External coding agents via `cloud_agent_*`.

### 3.3 Verification / self-check mechanisms (runtime)
- No generic "verifier agent" loop was found; verification is mostly **structural**: (a) `ExternalEffect` rows with idempotency keys and a status machine so every side-effecting call executes once and uncertain outcomes are surfaced (`run-effects.ts`, `approval-effect.ts`, `approval-effect-key.ts`); (b) `tool-completion-audit.ts` records failed/successful tool results (including MCP `isError`) without altering what the model sees; (c) loop guard (`tool-loop.ts`); (d) missing-final-response guard: a run that did tools but ends with no reply fails with `MISSING_TOOL_FINAL_RESPONSE_ERROR` rather than posting empty "done"; (e) approval and read-trust gating (below). The docs' "Important effects are verified independently" (`VISION.md`) is implemented in the test harness (section 6): graders read the demo website's own records instead of trusting the bot.

## 4. Memory (`docs/memory.md`, `packages/memory/src/index.ts`, `packages/adapters/src/memory-*.ts`)

Types:
1. **Markdown documents** - `MemoryDocument` (`spaceId,userId,botId?,scope,path,content,revision`) + append-only `MemoryRevision` (with `sourceRunId`, `sourceThreadId`) (`schema.prisma` ~1266). Scopes: `bot` (private to a bot) and `user` ("Shared memory", across bots in a space). Default doc path `MEMORY.md`. `MarkdownMemoryStore` implements `MemoryStore` (read/search/commit/remove/export, optimistic revision conflict -> `MEMORY_REVISION_CONFLICT_ERROR`). Search is plain case-insensitive substring over path+content (`index.ts` lines 44-60) - no embeddings.
2. **Prompt injection of memory**: every run loads bot + user memory, sorts by recency, packs into <= 32 KB inside `<durable_memory>` tags, framed as "data rather than instructions"; bot docs truncated from the end, user docs from the start (`memory-context.ts`).
3. **Writes**: model calls `remember` (append a fact to `MEMORY.md`, never replace; re-read+retry on revision conflict; `run-tools-memory.ts`, `appendMemoryFact`) or `save_shared_memory`. No separate background "memory extractor" process was found **(inferred: memory writing is purely model-initiated via tools plus prompt guidance)**. Users can view/download/delete notes (settings), and documents are portable markdown.
4. **Semantic memory providers (optional, pluggable)**: Supermemory (`supermemory-memory-provider.ts`), Serenity (`serenity-memory-provider.ts`, recall-only option), Honcho (`honcho-memory-provider.ts`, read-only). Configured per space (`SpaceMemoryConfig`, default scope isolated|shared), expose `save_memory/recall_memory/forget_memory` only when configured (`memory-tools.ts` `selectMemoryTools`); also used for automatic recall of out-of-window context (`formatRecalledMemory`).
5. **Thread history** as memory: compaction summary + `search_history/read_history` (section 2.6).
6. **Open work** (`ScratchpadItem`): a short per-bot to-do list shown in the UI.
7. Boundary: "Memory never crosses spaces." Encryption per space.

## 5. Routines, approvals, skills, plugins, import

### 5.1 Routines (`docs/routines.md`, `model Routine`, `run-routines.ts`, `routine-watch.ts`, `routine-coalescing.ts`)
A routine = a stored **prompt** + triggers on a bot ("Routines remain scheduled prompts rather than becoming a visual workflow language" - `VISION.md`). Fields: `crons[]`, `timezone`, `active`, `webhookEnabled`, `githubEnabled`, `messageProvider` (Slack message trigger), per-routine model, `watch`/`watchState`, `accountFailures`.
- **Cron**: a Graphile `routine.wakeup` job at `nextRunAt` (replaceKey per routine); wakeup claims the row in a transaction (`updateMany where nextRunAt = scheduledAt`), creates Task+Run (`trigger:"routine"`), computes next tick. One-shot via special cron form. Timer runs use a deterministic `clientNonce` for exactly-once; pending catch-ups are **coalesced** (one pristine pending run per routine); runs >15 min late are told both times so the agent can adapt, never skipped (`routine-lateness.ts`). Account-level model refusals back off the schedule (`routine-backoff.ts`). Retry of failed routine run at most once (`retryOfRunId @unique`, `routine.retry`).
- **Change/watch trigger**: checker never calls a model - it fingerprints files/folders, a command's output, or a read-only connector tool and only creates a run if changed (`routine-watch.ts`; watch tools must be explicitly read-only and allowed by approval rules, `watchToolRefusal` in `action-approval.ts`; watch-by-command always asks).
- **Webhook** (URL + key, `webhookSecretId`), **GitHub event** (`apps/api/src/github-webhook.ts`), **Slack message** (via messaging pipeline `messaging-inbound.ts`, `@chat-adapter/slack` etc.). Inbound routine runs wrap the routine's prompt first and the untrusted payload after, matched exactly (`packages/core/src/inbound-routine.ts`) so payload text can't impersonate owner instructions; such runs get stricter approval rules.
- Bots can create routines themselves via `schedule_*` tools (approval-exempt) and `create_child_routine`.
- Messaging: Slack/Telegram/WhatsApp/iMessage(Photon)/Lark adapters (`packages/adapters/src/photon`, `lark`, `chat-sdk-surface.ts`).

### 5.2 Approvals (`docs/approvals.md`, `packages/core/src/action-approval.ts`, `run-tool-gate.ts` 848 lines, `auto-review.ts`, `ActionApprovalRule`)
- Modes: **Ask** (changes ask; reads usually don't), **Auto** (a separate approval LLM, `auto-review.ts`, judges each action against the owner's words; asks if off-task or irreversible-unrequested; unsure/error -> ask), **Never ask**. Deployment picks default (`VISION.md`). Optional external verifier "Jev" (TypeSafe) selectable via env, `jev-auto-review.ts`.
- Allow/Block lists of exact tools or sites, grown from card buttons ("Allow once / Always allow / Deny"); block always wins, no card. Preview endpoint.
- Classification code: static sets in `action-approval.ts` (approval-exempt, required, explicit-required, unattended-safe builtins) and name-pattern heuristics for connector tools (`MUTATING_CONNECTOR_PATTERN` vs read-only pattern; declared `readOnly:false` always asks; compound "_and_" names ask).
- "Always asks": instruction/model changes, `create_space`, actions steerable by untrusted text (webhook-started writes, run "tainted" after outside content: `isRunTainted`, `run-trust.ts`, read-trust per connector), watch-by-command, new sites found in outside content (`outboundSiteGate`, `newSiteOutcome`).
- Flow: tool gate (`run-tool-gate.ts`) records an `ExternalEffect`, `pauseForApproval` builds an approval card block (`approval-ask.ts`), run goes `waiting_input` with turn checkpoint, **chat is never blocked** (`VISION.md`), user answers whenever; on answer the run resumes (`resume` trigger) and the exact approved arguments execute once. Repeating a denied action is detected (`repeatsDeniedAction`). Audit events recorded (`recordAuditEvent`).

### 5.3 Skills (`docs/skills.md`, `packages/core/src/agent-skill.ts`, `skill-tools.ts`, `builtin-skills.ts`)
- Format: Claude Agent Skills `SKILL.md` with YAML frontmatter (`name` <=80, `description` <=2000) + markdown body; unknown frontmatter keys preserved; plugin skills may carry text reference files (`AgentSkill.files`). Source = user | builtin | plugin; only user skills writable by tools. Stored in DB (`AgentSkill`), NOT on the bot's filesystem; the **catalog (name+description) is injected every turn** and `skill_read` loads a body on demand (`formatSkillsCatalogInstruction`); `/skill` in the composer or "use skill: x" forces one (`promptInvokesSkill`, `expandSkillReferencesInPrompt`, also inside routine prompts). Builtin skills are code constants (`builtin-skills.ts`, e.g. "Interrogate" adversarial review). Skills from GitHub/plugins are instructions only; scripts never run.
- **Taught skills**: demonstrate on the bot's screen ("Teach a task"); events recorded (`teach-recording.ts` with `sensitive` events stripped of key/text) are turned into a `SkillPlaybook` (whenToUse, inputs, steps, howToCheck, whatToReturn, approvalBoundaries, failureHandling) shown as an editable "Draft skill" card (`teach-playbook.ts`, `TaughtSkill`, `teaching-session.ts`).
- Repo-level `.agents/skills/` (composio, pr-watch) and `skills-lock.json` (pins `composio` from ComposioHQ/composio with a content hash) are **contributor/dev-tooling skills for coding agents working on the repo**, not the product runtime's skill store **(inferred from path, content of `.agents/skills/pr-watch/SKILL.md`, and absence of any runtime reader found)**.

### 5.4 Plugins (`docs/build-a-plugin.md`, `plugin-connectors.ts`, `plugin-marketplace.ts`, `plugin-catalog.ts`, `CapabilityInstall`)
Agent Plugins format (`plugin.json` + `mcp.json` + `skills/<name>/SKILL.md`, optional `commands/*.md` -> `/name` skills, `agents/*.md` -> skills that instruct `run_subagent`). Only remote HTTPS MCP (`streamable-http`/`sse`) and skills; no hooks, no local MCP, no scripts, no secrets in files, no `${VAR}`. Installed pinned to a commit; marketplace submissions reviewed. Examples in `examples/plugins/`. Also reads Agent Plugins 1.0.0 and legacy `.cursor-plugin`/`.grok-plugin`. Philosophy (VISION): plugins are "ordinary connectors and skills rather than a runtime of their own".

### 5.5 Import an agent (`docs/import-an-agent.md`, `packages/core/src/agent-import/` with `openclaw.ts`, `hermes.ts`, `stock.ts`, `credentials.ts`; `apps/api/src/agent-import*.ts`; `AgentImport` table)
Parses an OpenClaw/Hermes home folder or backup (folder read on-device; `.env`/`auth.json` only with consent) or a pasted description from ChatGPT/Claude/Gemini (a "Copy prompt" asks the old assistant to write down name, instructions, memories, procedures). User ticks items: instructions (SOUL.md/AGENTS.md) -> bot instructions; MEMORY.md/USER.md/daily notes -> bot or shared memory; skills; model; MCP servers (ask-before-use); scheduled jobs -> routines **paused**; API keys -> model connections. Risky items (skills, MCP, routines, key-like text) start unticked. A checklist card (`import_setup` block) lists leftover actions. Strong migration/onboarding hook; code-executing things are not auto-enabled.

## 6. Evals and quality mechanisms (`docs/agent-verification.md`, `docs/context-and-evals-tasks.md`, `docs/evals/`, `packages/testkit/`)

Layered test strategy (table in `agent-verification.md`): fast tests with the scripted runtime; **Pi protocol regressions** using a loopback OpenAI-compatible model emulator (`packages/testkit/src/model-emulator.ts`, validates each actual request and requires all steps consumed); Postgres "product journey" integration tests with real executor + Pi + emulated model (`pi-offline.postgres.test.ts`, `executor-turn-checkpoint.test.ts`, `computer-approval.postgres.test.ts`); computer replay in Docker with real Chromium and a recorded decision fixture ("closed vocabulary", no prose/URLs/IDs) from a live Luna run; live vision acceptance (`computer-use.e2e.test.ts`) against Boat/E2B incl. destroy-and-recover; **live flows** (`packages/testkit/src/flows/`: `weekly-shopping`, `freshcart` demo site, `connect-mcp`) where a **second LLM plays the user** from a private brief (`simulated-user.ts`), answers cards, takes over the screen, with grading from the demo website's own records and a versioned judge rubric that checks the bot's claims against them ("the bot's claims are not evidence"); HTML report with chat + screen. `pnpm test:evals` (`packages/testkit/src/evals/`: tool-choice, silence, clarification, approval, history, cache-probe/cache-budget, wire-observer, step-accounting, judge, with a cumulative spend guard defaulting to USD 5).
Notable discipline: missing live creds = "not run" not "pass"; preserved failed reports; decision gates (zero unauthorized reads, pass all distant-recall samples before choosing a context strategy, publish n/CI); the history/context study (`docs/context-and-evals-tasks.md`, `docs/evals/history-findings.md`) shows a rejected default (snapshots failed 2 of 12 distant samples) and measured costs (e.g. adaptive policy ~28% cheaper on a 100-message workflow, 3 trials, caveated). Runtime metrics for response latency are logged (section 2.5). Unit-level: `retry-policy`, `secrets-guard.ts` redaction on all tool output, `ai-consent`.
Not found: an automatic in-product regression eval running on user data, or online LLM-as-judge of live runs (apart from the Auto approval reviewer).

## 7. What is strong / novel vs ordinary

**Genuinely strong or distinctive**
1. **Pause-on-human, release-compute design with transcript checkpoints** keyed to original tool-call IDs plus idempotent `ExternalEffect` rows, lease fences and fenced finalization: approvals/questions/takeovers never hold a worker and survive deploys. Rarely done this carefully in open source agents.
2. **Cache-economics-aware context management** (`rebuildPaysOff` break-even math, byte-stable prefix, newest-first whole-result retention, free deterministic selection, explicit rule that cache expiry never triggers paid compaction) backed by an eval study with published failures.
3. **Trust/taint model for prompt injection**: runs tainted by outside content, read-trust per connector, webhook/channel runs lose fleet tools and cross-chat search, inbound routine prompts matched exactly before untrusted payload, "untrusted data" framing on memory/summaries/history, new-site egress gating, Auto reviewer that sees only the owner's words (not page content). Concrete and widely wired in code.
4. **Dispatch without a queue on the hot path** (start in the API process, memory-based admission, durable recovery scan + leader reconciler, Graphile for scheduled jobs) giving low first-response latency, with SLO-style timing logs.
5. **Live-flow evals with a simulated user model and grading by the world's records**, plus recorded-decision computer replay. Strong pattern for agent QA.
6. **Persistent identity model**: one continuous thread per bot with steering instead of queueing, memory/versioned instructions/undo, Team vs Private computer with checkpointed workspace and screen takeover leases.
7. **Importers** (OpenClaw/Hermes/ChatGPT) and plugin format compatibility (Agent Plugins, Cursor, Grok) as acquisition mechanics.
8. Lazy connector catalog and per-bot tool disabling for context hygiene; model fallback chains with credential-rotation handling and subscription OAuth (use your ChatGPT/Claude plan).

**Ordinary / thin**
- The agent loop itself is Pi, not original; subagents are a single level (max 4 parallel), no planner/critic loop, no automatic result verification beyond effects, guards and approvals.
- Memory is markdown append + substring search; true semantic recall is outsourced to optional third-party providers; no automatic memory extraction/consolidation pass found.
- Peer-bot "collaboration" is async messaging with a hop cap; no shared task graph except the ticket board.
- Skills are prompt text only; no skill eval/versioning beyond editing; the repo's `.agents/skills` and `skills-lock.json` are dev tooling.
- Docs and code diverge in spots (e.g. `fleetManagement` default).
